# 두 기후리스크 모델 비교 — 원본(PLANiT/climate_risk) vs 재구축본(CLIMADA 기반)

물리적 기후리스크 평가 도구를 **파라메트릭 통계 방식**에서 **CLIMADA 확률적 이벤트셋 방식**으로
재구축하면서 데이터 소스·API·방법론이 바뀌었다. 본 문서는 그 변경 내용과, 변경으로 인해
새로 생기거나 사라지는 리스크를 정리한다. 모든 내용은 두 저장소의 실제 코드를 대조해 확인했다
(2026-09-01).

| | **원본 — PLANiT-Institute/climate_risk** | **재구축본 — climaterisk (CLIMADA)** |
|---|---|---|
| 엔진 | 자체 파라메트릭 통계 모델 | CLIMADA 6.1 (ETH 취리히, 과학 검증) |
| 스택 | Streamlit + FastAPI, numpy/pandas | React + FastAPI + CLIMADA 워커(conda 격리) |
| 위험 표현 | 통계 분포(Gumbel/Poisson)의 수식 적합 | 확률적 이벤트셋(수만 개 합성 사건) |

---

## 1. API·데이터베이스가 어떻게 바뀌었나

### 1.1 해저드(재해) 데이터 — 근본 전환

| 재해 | 원본 | 재구축본 |
|---|---|---|
| 태풍 | Open-Meteo 풍속이력 → 지역 Poisson 빈도 × HAZUS 피해율 | CLIMADA Data API — IBTrACS 합성트랙 **43,560개** 이벤트셋 |
| 홍수 | Open-Meteo 강수이력 → Gumbel 재현주기 | CLIMADA Data API — ISIMIP 하천홍수 침수심 |
| 지진 | (해당 없음/제한적) | CLIMADA Data API — 관측 카탈로그 **41,710개** 이벤트 |
| 산불 | Open-Meteo 파생 지수 | CLIMADA Data API — 관측 밝기온도 |
| 미래 시나리오 | IPCC 전지구 **증가율 배수**를 현재값에 곱함 | RCP별 **미래 이벤트셋 자체**를 교체 |

**한 문장 요약**: 원본은 *"지점의 과거 날씨를 받아 재해 통계를 직접 계산"*, 재구축본은
*"과학팀이 만든 재해 시뮬레이션을 받아 자산에 적용"*.

### 1.2 외부 API 의존성

| | 원본 | 재구축본 |
|---|---|---|
| 실시간 외부 API | **Open-Meteo 아카이브 API** (유일, 자산 좌표마다 실시간 호출) | **자산 좌표별 기상 API 호출 없음** — 해저드는 CLIMADA Data API에서 받아 로컬 카탈로그(HDF5)에 캐시하면 오프라인 실행 가능(카탈로그 미스 시 Data API 실시간 조회; 예보·공급망 모드는 별도 다운로드) |
| NGFS/IPCC/배출계수 | 코드 내 하드코딩 상수 | 번들 라이브러리(JSON) + NGFS pyam |
| 인구·노출 | 샘플 시설(`sample_facilities.py`) | WorldPop/LitPop/GPW (선택), 사용자 자산 |

### 1.3 데이터 카탈로그(재구축본이 새로 도입)

`data/hazard_db/`에 `(재해, 시나리오, 지역, 연도)` 키로 HDF5 해저드를 색인. 러너가 **로컬
카탈로그 우선 → 없으면 Data API 폴백**. 방화벽/폐쇄망에서 1회 반입 후 완전 오프라인·재현
가능한 구조. 원본에는 없는 계층.

## 2. 방법론 차이가 만드는 실질적 결과

| 축 | 원본(파라메트릭) | 재구축본(이벤트셋) | 왜 중요한가 |
|---|---|---|---|
| 포트폴리오 상관 | 지점 **독립** 계산 | 하나의 사건이 여러 자산 **동시 타격** | 한 태풍이 부산+울산을 함께 치는 꼬리위험. 파라메트릭은 이를 과소평가 |
| 재현주기 | 분포 수식으로 임의 T 산출 | 이벤트 기록 길이에 **자동 상한**(태풍 344년/지진 57년/산불 10년) | 기록이 못 받치는 꼬리값의 무분별한 산출을 구조적으로 차단 |
| 미래 반영 | 전지구 배수 곱셈 | 시나리오별 물리 이벤트셋 | 지역·계절 구조가 배수로 뭉개지지 않음 |
| 재무 연계 | 자산별 EAL + 사업중단손실(BI) | AAI + DSCR/신용등급/스프레드 + 적응 비용편익(태풍 한정) + Sobol 불확실성(태풍 한정) | 실증: 이 포트폴리오는 전환리스크 NPV가 물리 NPV의 3.5배 |
| 검증 가능성 | (검증 데이터 미연동) | E-OBS 관측 대조 선례 있음(유럽) | 모델값을 실측과 맞대볼 수 있음 |

**주의 — 원본을 폄하하지 말 것**: 원본의 HAZUS·Poisson·Gumbel·SSP 조정·사업중단손실은
정통 파라메트릭 재해평가 방법이며 잘 구현돼 있다. 차이는 "확률을 어떻게 만드는가" 한 축이고,
그 축의 우열이 아니라 **용도 적합성**의 문제다.

## 3. 변경으로 생기는 리스크 (양방향)

### 3.1 재구축본 채택으로 **사라지는** 리스크
- **폐쇄망 실행 실패** — Open-Meteo 실시간 호출이 방화벽에 막히면 원본은 조용히 하드코딩
  기본값으로 폴백(`data_source: "hardcoded_config"`). 재구축본은 애초에 그 API를 안 쓰고
  로컬 캐시로 돌아 이 리스크가 없다.
- **포트폴리오 상관 과소평가** — 위 §2 참조.
- **과잉 외삽** — 재현주기 자동 상한으로 근거 없는 꼬리값 산출을 차단.

### 3.2 재구축본에서 **새로 생기거나 남는** 리스크
- **국내 특화 미완** — 재구축본도 CLIMADA **전지구** 데이터를 쓴다. "CLIMADA라서 자동으로
  국내 정밀"이 아니다. KMA 온램프는 코드에 존재하나 실제 한국 자료로 돌린 검증은 아직 없다.
  → 국내 해상도가 필요한 공시에 그대로 쓰면 정밀도 리스크.
- **취약성 곡선의 불확실성** — Sobol 분해상 모델 불확실성의 **83%가 취약성 곡선**에서 발생
  (글로벌 기본 곡선 사용). 국내 손실자료(EM-DAT 등) 보정 전 절대값은 신뢰구간과 함께만 유효.
- **운영 복잡도 상승** — CLIMADA + conda 워커 + GPL 경계 격리. 원본(Streamlit)보다 배포·유지가
  무겁다. 다수 자산 일괄 분석 시 워커 병렬·해저드 캐시 설계가 필요.
- **대용량 1회 다운로드** — 공급망(MRIOT ~900MB), 인구(WorldPop/GPW) 등 일부 기능은 초기
  데이터 확보가 전제.
- **폭염 사망 등 커스텀 페릴은 검증 미완** — CLIMADA에 없는 페릴을 얹은 것으로, MoMo 정렬
  전이라 극단 연도 과소예측(약 2.3배)이 남아 있다. 완성본으로 제시하면 신뢰 리스크.

### 3.3 두 도구 **공통**으로 남는 리스크
- 취약성/피해곡선이 해외 기준(HAZUS는 미국, CLIMADA 기본은 글로벌) → 국내 보정 공통 숙제.
- 배출·전환 파라미터의 자산별 실측 부재 시 섹터 프록시 의존.

## 4. 결론 — "재구축본을 쓰면 해결되나?"

| 질문 | 답 |
|---|---|
| Open-Meteo 방화벽 문제 | **해결** — 그 API를 쓰지 않음 |
| 포트폴리오 꼬리위험·미래 시나리오 정합 | **개선** — 이벤트셋 방식의 구조적 이점 |
| 재무·적응·불확실성 분석 | **확장** — 원본에 없던 체인 (한국 사례 실증 완료) |
| 국내 해상도 특화 | **미해결 (공통)** — CLIMADA 전환만으로는 안 되고 KMA 데이터 연동 필요 |
| 취약성 정밀도 | **미해결 (공통)** — EM-DAT 등 국내 보정 필요 |

즉 **방법론은 한 단계 위이나, 국내 특화와 취약성 정밀도는 어느 도구든 별도의 국내 데이터
작업이 전제**다. 이 두 가지가 다음 우선순위다.
