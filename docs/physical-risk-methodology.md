# Physical-risk methodology — CLIMADA-based asset-level assessment

Phase 2, 2026-09-22. `climada 6.1.0` / `climada_petals 6.2.0`.

This describes the **new** physical-risk engine (`worker/climaterisk_worker/physical_risk/`
+ `src/climaterisk/physical_risk/`). It is separate from the legacy peril runners in
`physical.py`, which keep their behaviour and their results; §18 records where the two
differ and why.

The companion document [`impact-function-inventory.md`](impact-function-inventory.md) lists
every impact function the installed environment provides, generated by instantiating them.

## 1. Scope

Three hazards for Korean real-estate and facility assets:

| Hazard | CLIMADA tag | Status this phase |
|---|---|---|
| River flood | `RF` | Fully quantified |
| Tropical cyclone (wind) | `TC` | Fully quantified |
| Heatwave | `HM` / `HW` | **Hazard exposure only — no financial loss** (§7) |

Storm surge and TC rainfall are separate hazards and are not folded into the TC number.

**No impact function is authored in this repository.** The curves are CLIMADA's and
CLIMADA-Petals'. Korea-specific calibration is not performed and is not claimed.

## 2. Asset / exposure definition

Required per facility: `facility_id`, `facility_name`, `latitude`, `longitude`,
`asset_value_usd`. Optional and **recorded but not fed to the impact functions**:
`property_type`, `floor_area_m2`, `year_built`, `structure_type` — the published curves
take none of them, and passing them would imply a sensitivity the functions do not have.

The one exception is `property_type`, which selects *which* JRC sector curve is used (§5).
That mapping is a platform choice, kept in configuration, not something the JRC defines.

Each facility becomes a one-row CLIMADA `Exposures` with `value = asset_value_usd`,
`value_unit = "USD"`. LitPop is available from the Data API as an alternative exposure but
means something different (a gridded asset-value proxy, not the portfolio); the two are
never mixed in one result. Population rasters are never used as asset value.

## 3. Hazard definition

A CLIMADA `Hazard`: an event set with per-event intensity at centroids and a `frequency`
in events per year (`frequency_unit` `1/year`). The engine takes the hazard as given and
records where it came from; it does not build hazards.

`hazard_intensity` on a row is the **peak intensity over all events at the centroid nearest
the facility** — a locating number for the reader, not an input to the loss (the loss uses
every event).

## 4. CLIMADA impact functions used

| Hazard | Function | Source |
|---|---|---|
| `RF` | `ImpfRiverFlood.from_jrc_region_sector(region, sector)` | Huizinga et al. 2017 (JRC105688) |
| `TC` | `ImpfSetTropCyclone.from_calibrated_regional_ImpfSet()`, id by country | Eberenz et al. 2021 (NHESS 21:393-415) |

Both are called directly and used unmodified. The registry reads their `haz_type`, `id`,
`name`, `intensity_unit`, range, MDD and PAA off the instantiated object, and those values
travel into every result row.

## 5. Flood methodology

`ImpfRiverFlood.from_jrc_region_sector("Asia", sector)` — 11 points over 0–12 m, MDD 0–1,
PAA flat at 1 (CLIMADA's own "noPAA" curves).

`property_type` → JRC sector comes from `assets/libraries/physical_risk_config.json`:
office/retail/hotel → `commercial`, warehouse/logistics/factory/data_center →
`industrial`, residential/apartment → `residential`, and so on, defaulting to
`commercial`. **This mapping is ours, not the JRC's.** An unmapped type takes the default
rather than a guess.

Region is `Asia` for Korean assets. The six continents are available; the engine does not
interpolate between them.

## 6. Tropical-cyclone methodology

The regional function is chosen by **CLIMADA's own country table**, not by reading a region
label: `ImpfSetTropCyclone.get_impf_id_regions_per_countries(["KOR"])` returns
`([9], ['WP4'], ['North West Pacific'])`. Korea therefore uses impact function **id 9**,
`v_half` 190.5 m/s, `v_thresh` 25.7 m/s. Japan resolves to the same function; China to id 8
(`WP3`, China Mainland).

A country absent from CLIMADA's table falls back to CLIMADA's own id 10, *Rest of The
World*, and the row says so.

Only **wind** is modelled. A TC's surge and rainfall are different hazards with different
impact functions; combining them is out of scope for this phase and is not silently folded
into the TC loss.

## 7. Heatwave methodology — why there is no number

`climada.entity.impact_funcs` contains `base`, `impact_func_set`, `storm_europe`,
`trop_cyclone`. `climada_petals.entity.impact_funcs` adds `drought`,
`relative_cropyield`, `river_flood`, `wildfire`. **There is no heat, thermal, mortality or
UTCI impact function in either**, verified by module enumeration rather than by reading
documentation.

Therefore a heat hazard produces:

```
calculation_status      = HAZARD_ONLY
hazard_intensity        = <reported>
potential_loss_usd      = null
eal_usd                 = null
eal_as_pct_of_assets    = null
risk_level              = null
```

`0` would assert that the loss was computed and came out zero. It was not computed.

Authoring a cooling-cost, energy-cost, productivity or building-damage function for heat is
explicitly out of scope: it would be this repository's curve presented alongside published
ones. The repository's separate `heat_mortality` peril is a different thing — a custom
mortality model with its own provenance record
([`HEAT_MORTALITY_PROVENANCE.md`](HEAT_MORTALITY_PROVENANCE.md)) — and is not used here,
because it produces deaths, not currency.

## 8. Potential loss

Loss at a stated return period, read from `Impact.calc_freq_curve([T])`. The representative
`T` is configuration (`potential_loss.return_period_years`, currently 100). Every row
carries `potential_loss_return_period_years` alongside the amount, so the number is never
ambiguous about which return period it is.

**The saturation guard.** `calc_freq_curve` does not return NaN beyond what the event set
can express — it returns the largest event's loss. A four-event set at 0.1/yr asked for a
100-year loss returns the 10-year loss under a 100-year label. The engine therefore computes
the ceiling `1 / min(frequency)` first and, when the request exceeds it, reports

```
calculation_status = RETURN_PERIOD_NOT_RESOLVABLE
potential_loss_usd = null
```

with the ceiling named in `status_detail`. **EAL survives this status**, because EAL uses
every event's frequency and needs no extrapolation — it is the one financial field that
remains valid, and the row keeps its risk level.

This is not hypothetical: the CLIMADA observed-track TC set for Korea (3,890 events,
1980–2020) has a 41-year ceiling, so its 100-year PML is refused.

## 9. EAL

`Impact.aai_agg` — CLIMADA's expected annual impact, in the exposure's currency. Verified
identity (`tests/test_physical_risk_engine.py`):

```
aai_agg == Σ(at_event × frequency)
```

The engine reads it; it does not re-implement it.

```
eal_as_pct_of_assets = eal_usd / asset_value_usd × 100
```

`null` when `asset_value_usd` is zero or missing — the loss may be real, but as a share of
assets it is undefined.

## 10. Probability, return period, frequency — three distinct things

| Term | Definition here |
|---|---|
| `frequency` | CLIMADA `Hazard.frequency`: events per year, `frequency_unit` `1/year`. |
| `return_period_years` | `1 / cumulative annual exceedance frequency`, as produced by `calc_freq_curve`. |
| `probability` | `1 / return_period_years`. |

The engine **derives probability from the return period** rather than storing them
independently, so they cannot disagree.

**Where this is approximate.** CLIMADA's frequency is an exceedance *frequency*. For rare
events it is numerically close to an annual exceedance *probability*; for frequent events
(frequency ≥ 1/yr) they diverge, because a probability cannot exceed 1 and a frequency can.
The engine does not convert between them with a Poisson correction, and rows carry the
definitions in a `definitions` field so a reader can see which convention produced the
number.

## 11. Risk level

| Band | Criterion |
|---|---|
| Low | EAL/Asset < 0.10% |
| Medium | 0.10% ≤ EAL/Asset < 0.50% |
| High | EAL/Asset ≥ 0.50% |

**This is climaterisk's own methodology within a GRESB-informed framework. It is not an
official GRESB threshold**, and must not be described as one. GRESB informs *what* is
assessed — acute/chronic hazard identification, financial impact, forward-looking scenarios
— not these cut-offs.

The bands live in `assets/libraries/physical_risk_config.json` and can be changed without
touching the calculation; a test asserts the literals do not appear in the code. Each row
records the criterion string it matched (`risk_level_criteria`).

## 12. Climate-change multiplier

```
climate_change_multiplier = future_EAL / baseline_EAL
```

Computed **only** from two real runs, with `baseline_period`, `future_period`,
`baseline_scenario`, `future_scenario` and both EALs recorded so it is reproducible. Where
either run has no EAL, or the baseline is zero, the multiplier is `null` and the reason is
stated. No constant is ever configured in its place.

Measured example (this repository, Data API, 100 M USD facility in Seoul): TC
historical 1980–2020 EAL \$2,511 → rcp45 2040 EAL \$3,976, multiplier **1.5833**.

For flood the Data API currently exposes a single climate scenario (`rcp26`), so no
baseline/future pair exists and the multiplier is `null`.

## 14. Hazard replacement — three models

Phase 3 replaced the two-way `GLOBAL_BASELINE` / `KOREA_HAZARD` split with three models
that differ **only** in hazard source and share exposure and impact function:

```text
GLOBAL_BASELINE   Data API, spatial_coverage=global          — global reference calculation
DATA_API_COUNTRY  Data API, spatial_coverage=country (KOR)   — country-specific Data API calculation;
                                                                NOT Korea-local source data
KOREA_LOCAL       domestic source via its own adapter         — reported only when a domestic dataset
                                                                and compatible adapter actually exist
```

Flood and TC `KOREA_LOCAL` adapters are `NOT_IMPLEMENTED` (no dataset connected); heat is
`HAZARD_ONLY` on KMA data. Full definitions, readiness table, adapter contract and measured
rows: [`physical-risk-models.md`](physical-risk-models.md),
[`korea-hazard-replacement.md`](korea-hazard-replacement.md). `KOREA_HAZARD_EXPOSURE` was
dropped: exposure stays the user portfolio in every model, and no Korean asset-value
dataset is fabricated.

## 15. Comparison methodology

`compare_models(rows, baseline_model, comparison_model, facility_id, hazard_type)` is
source-independent; the two rows must describe the same facility and hazard. Three change
forms are kept apart:

```text
change_pct = (comparison / baseline − 1) × 100     relative, percent; null when baseline is 0 or missing
change_usd = comparison − baseline                  absolute, USD
change_pp  = comparison_pct − baseline_pct          percentage points (0.61 % → 0.77 % is +0.16 pp)
```

`requested_scenario` and `served_scenario` are separate fields; a dataset that answers
`rcp45` with `rcp60` yields `SCENARIO_MISMATCH` with null financials rather than a number
filed under the requested key. A model-vs-model ratio is a hazard-source comparison and is
never reported as a climate-change multiplier (§12 requires two runs of the same model).

## 16. Data provenance

Every row carries `hazard_source`, `exposure_source`, `impact_function_source`,
`impact_function_id`, `impact_function_name`, `scenario`, `time_horizon`, `data_version`
and `model_id`. The impact-function source string names the exact constructor call, e.g.
`ImpfRiverFlood.from_jrc_region_sector(region='Asia', sector='commercial')`.

## 17. Calculation status

| Status | Meaning | Financial fields |
|---|---|---|
| `FULL` | Priced with a published impact function | populated |
| `HAZARD_ONLY` | Hazard present, no applicable impact function (heat) | **null** |
| `NO_IMPACT_FUNCTION` | Hazard tag not in the registry | **null** |
| `NO_HAZARD_DATA` | No hazard for this facility | **null** |
| `NO_EXPOSURE_DATA` | No positive `asset_value_usd` | **null** |
| `RETURN_PERIOD_NOT_RESOLVABLE` | PML beyond the event set's ceiling | PML null, **EAL kept** |
| `ERROR` | The calculation raised | **null** |

Enforced in `ResultRow.finalise`, not left to callers, and tested per status.

## 18. Legacy vs this engine — the flood difference

The legacy runner (`physical._flood_impf_set`) rebuilds an `ImpactFunc` from an 8-point
resample of the JRC curve stored in `assets/libraries/impact_function_presets.json`, at
depths 0/0.5/1/2/3/4/5/6 m. This engine calls `ImpfRiverFlood` directly: **11 points over
0–12 m**.

The two therefore produce different numbers for the same hazard, exposure and frequencies,
and that is expected. The difference is attributable to the curve alone — a test holds
hazard, exposure and frequency identical and varies only the function. Legacy results are
not migrated, not corrected and not deleted; they live in their own tables.

## 19. Limitations

* **This version uses existing CLIMADA impact functions. Korea-specific calibration is not
  performed.** No curve here is fitted to Korean loss experience.
* **Heatwave financial loss is calculated only where an applicable existing CLIMADA impact
  function is available** — at `climada 6.1.0` / `climada_petals 6.2.0` there is none, so
  no heat loss is produced.
* The `property_type` → JRC sector mapping is a platform choice, not a published one.
* TC covers wind only. Surge and rainfall are absent, so a TC total is not a total typhoon
  loss.
* `hazard_intensity` is a nearest-centroid peak, a locating figure rather than the quantity
  the loss integrates.
* Probability and exceedance frequency are treated as interchangeable; see §10 for where
  that breaks down.
* Flood has no baseline/future scenario pair in the Data API today, so its
  climate-change multiplier is null.
* `KOREA_HAZARD_EXPOSURE` is schema-only.
* Exposure is a point per facility; sub-facility footprints are not modelled.

## 20. Future Korea-specific impact-function calibration

Out of scope here, and a prerequisite for calling any of this "Korean". It would need
Korean observed losses by hazard, an exposure definition matching them, and the
comparability gate that already exists for the 재해연보 series
([`OBSERVED_LOSSES_KR_SPEC.md`](OBSERVED_LOSSES_KR_SPEC.md) §6-1) — which currently refuses
TC calibration because the observed figure aggregates wind, surge and rain while the model
carries wind alone. That refusal applies to this engine too.
